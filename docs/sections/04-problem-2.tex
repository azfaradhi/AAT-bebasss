\section{Problem 2: Concurrency, Availability, dan Graceful Degradation}
\begin{infobox}{Pertanyaan Utama}
Bagaimana sistem tetap responsif saat BMKG dan PVMBG memiliki latensi berbeda,
menangani lonjakan permintaan, dan tetap melayani data yang tersedia ketika
salah satu sumber mengalami outage?
\end{infobox}

\subsection{Rancangan Solusi}
Problem ini memisahkan jalur pembaruan data dari jalur pembacaan client.
Aggregator mengambil data BMKG dan PVMBG secara berkala, menyimpannya pada
Canonical Store, sedangkan Client API membaca data yang sudah tersedia melalui
API internal Aggregator. Dengan pemisahan tersebut, client tidak perlu
menunggu panggilan langsung ke sumber eksternal yang lambat pada setiap
permintaan \texttt{GET /hazard-events}.

\subsubsection{Tiga Risiko yang Ditangani}
Rancangan ini menangani tiga kegagalan. \textit{Head-of-line blocking} terjadi
ketika pengambilan data BMKG dan PVMBG dilakukan sekuensial sehingga sumber
cepat tertahan oleh sumber lambat. \textit{Resource exhaustion} terjadi ketika
polling tumpang-tindih atau panggilan ke sumber lambat tidak dibatasi.
Ketiadaan degradasi terkendali terjadi ketika satu sumber gagal dan seluruh
respons client ikut gagal, padahal data terakhir masih tersedia dan berguna.

\subsubsection{Model Konkurensi dan Isolasi Sumber}
Model konkurensi yang dipilih adalah asynchronous I/O Node.js. BMKG dan PVMBG
tidak berbagi satu siklus polling bersama -- masing-masing sumber memiliki
\textit{interval timer} independen sendiri yang berjalan secara asynchronous dan
paralel satu sama lain.

Setiap sumber memiliki guard \textit{in-flight} miliknya sendiri: tick berikutnya
untuk sumber yang sama dilewati apabila tick sebelumnya milik sumber itu masih
berjalan, tetapi ini tidak memengaruhi sumber lain sama sekali. Dengan demikian,
PVMBG yang lambat atau macet tidak pernah menunda ataupun melewatkan tick BMKG
-- BMKG tetap berjalan sesuai jadwalnya sendiri. Kegagalan satu sumber juga
tidak membatalkan hasil sumber lain. Pendekatan per-sumber independen ini
mencegah ledakan request ke sumber eksternal ketika PVMBG memiliki latensi
tinggi, sekaligus menghilangkan \textit{head-of-line blocking} antar sumber
sepenuhnya, bukan hanya mengurangi dampaknya dalam satu siklus bersama.

Setiap panggilan keluar mempunyai timeout yang dikonfigurasi melalui
\texttt{SOURCE\_REQUEST\_TIMEOUT\_MS} serta mencatat \texttt{latency\_ms} pada
log terstruktur. Untuk PVMBG, client sumber juga dibungkus oleh
\textit{circuit breaker} dan \textit{concurrency limiter}. Circuit breaker
membuka rangkaian setelah sejumlah kegagalan berturut-turut, menolak request
selama masa \textit{cooldown}, lalu mengizinkan satu percobaan pemulihan.
Concurrency limiter membatasi jumlah panggilan PVMBG yang aktif sesuai
\texttt{PVMBG\_MAX\_CONCURRENT\_CALLS}.

\subsubsection{Graceful Degradation dan Data Stale}
Jika polling suatu sumber gagal, Aggregator tidak menghapus event yang telah
tersimpan. Sebaliknya, sumber tersebut diberi penanda stale pada tabel
\texttt{source\_sync\_state}; respons pembacaan memuat
\texttt{meta.stale\_since}. Dengan demikian, client masih memperoleh data
terakhir yang diketahui sistem, sekaligus mengetahui bahwa sinkronisasi salah
satu sumber sedang bermasalah. Setelah polling sumber kembali berhasil,
penanda stale dihapus tanpa restart service.

Untuk mengurangi beban polling ketika histori bertambah, Aggregator menyimpan
waktu sinkronisasi sukses terakhir per sumber. Polling pertama mengambil data
yang tersedia, sedangkan polling berikutnya memakai parameter \texttt{since}
dengan overlap yang dapat dikonfigurasi melalui \texttt{POLL\_LOOKBACK\_MS}.
Event dalam overlap aman diproses ulang karena penyimpanan menggunakan upsert
berdasarkan pasangan \texttt{source} dan \texttt{source\_ref\_id}.

Keputusan sistem ketika polling PVMBG berhasil atau gagal dirangkum pada
Gambar~\ref{fig:problem-dua-graceful-degradation}. Diagram tersebut
menunjukkan bahwa kegagalan PVMBG tidak membatalkan pembaruan BMKG maupun
pembacaan data yang telah tersedia bagi client.

\subsection{Proof of Concept (PoC)}

\subsubsection{Uji Latensi BMKG-only}
Pengujian ini membuktikan bahwa keterlambatan PVMBG tidak menyebabkan
\textit{head-of-line blocking} pada request yang hanya membutuhkan data BMKG.
Langkah pembuktiannya adalah sebagai berikut.
\begin{enumerate}
  \item Atur \texttt{PVMBG\_DELAY\_MIN\_MS=3000} dan
  \texttt{PVMBG\_DELAY\_MAX\_MS=3000} pada \texttt{.env}, kemudian recreate
  hanya service PVMBG.
\begin{lstlisting}[style=code,language=bash]
docker compose up -d --force-recreate pvmbg-mock
\end{lstlisting}

  \item Skrip k6 membaca token client dari variabel environment
  \texttt{CLIENT\_JWT} (lihat baris 5 pada skrip k6 di bawah). Ambil token
  tepat sebelum menjalankan k6, agar token masih berlaku selama durasi uji.
  \texttt{ACCESS\_TOKEN\_TTL\_SECONDS} default (60 detik) sama persis dengan
  durasi uji sustained pada subbagian berikutnya; naikkan nilainya di
  \texttt{.env} (mis. 300) sebelum menjalankan uji beban berkelanjutan agar
  token tidak kedaluwarsa di tengah uji.
\begin{lstlisting}[style=code,language=bash]
export CLIENT_JWT=$(curl -s -X POST http://localhost:8091/auth/token \
  -H 'Content-Type: application/json' \
  -d '{"client_id":"lapangan-client","client_secret":"<AUTH_LAPANGAN_CLIENT_SECRET>"}' \
  | node -pe 'JSON.parse(require("fs").readFileSync(0)).access_token')
\end{lstlisting}

  \item Jalankan skenario \textit{k6}. Skenario ini mengirim request
  BMKG-only dan request vulkanik secara bersamaan.
\begin{lstlisting}[style=code,language=bash]
k6 run tests/phase6/p2-concurrency.k6.js
\end{lstlisting}

  \item Catat p95 workload BMKG-only. Hasilnya dirangkum pada
  Tabel~\ref{tab:problem-dua-latensi-bmkg}.
\end{enumerate}

\subsubsection{Uji Beban Berkelanjutan}
Tooling yang digunakan adalah \textit{k6} dengan script
\texttt{tests/phase6/p2-concurrency.k6.js}. Script menjalankan 50 virtual user
untuk request BMKG-only dan 10 virtual user untuk request vulkanik selama 60
detik secara sustained. Output pengujian harus melaporkan throughput,
p50, p95, p99, dan error rate. Sistem dinyatakan memenuhi kriteria apabila
error rate, di luar penolakan terkontrol seperti HTTP 429, berada di bawah 1\%
dan tidak terjadi crash.

Sama seperti sebelumnya, ambil \texttt{CLIENT\_JWT} tepat sebelum menjalankan k6
(lihat langkah 2 subbagian sebelumnya), dengan \texttt{ACCESS\_TOKEN\_TTL\_SECONDS}
dinaikkan agar token tidak kedaluwarsa sebelum uji 60 detik ini selesai.

k6 run tests/phase6/p2-concurrency.k6.js

\subsubsection{Outage dan Pemulihan PVMBG}
Pengujian ini membuktikan bahwa kegagalan PVMBG tidak menghentikan jalur
pembacaan client dan bahwa sistem pulih tanpa restart service.

\begin{enumerate}
  \item Kirim request \texttt{CLIENT API - /hazard-events} dengan
  \texttt{hazard\_type=VOLCANIC}. Terlihat bahwa request berhasil,
  berisi data vulkanik, dan \texttt{meta.stale\_since} bernilai
  \texttt{null}.
  \begin{figure}[H]
    \centering
    \includegraphics[width=0.5\textwidth]{figures/problem-2/2-3.png}
    \caption{Kondisi awal saat service aktif dan \texttt{stale\_since} bernilai \texttt{null}.}
    \label{fig:up-server-stale-since-null}
  \end{figure}

  \item Set variable \texttt{outage\_enabled=true} dan
  \texttt{outage\_duration\_seconds=30}, lalu jalankan request
  \texttt{PVMBG MOCK - /admin/outage}. Respons  menyatakan
  \texttt{outage\_active=true}.
  \begin{figure}[H]
    \centering
    \includegraphics[width=0.5\textwidth]{figures/problem-2/2-4.png}
    \caption{Membuat server down sesaat}
    \label{fig:outage-active-true}
  \end{figure}

  \item Tunggu sekitar 8 detik agar polling yang sedang berlangsung selesai
  dan Aggregator menjalankan polling PVMBG yang gagal. Kemudian jalankan
  kembali request \texttt{CLIENT API - /hazard-events} untuk \texttt{hazard\_type=VOLCANIC}.
  Respons vulkanik memuat data terakhir dari Canonical Store, sedangkan \texttt{meta.stale\_since} berisi waktu sejak kapan agregrator mendeteksi kegagalan sinkronisasi.

  \begin{figure}[H]
    \centering
    \includegraphics[width=0.5\textwidth]{figures/problem-2/2-5.png}
    \caption{\texttt{stale\_since} terisi saat PVMBG mengalami outage.}
    \label{fig:stale-since-terisi}
  \end{figure}

  \item Setelah durasi outage selesai, tunggu sekitar 8 detik agar satu polling
  pemulihan berhasil, lalu ulangi request vulkanik. Respons \texttt{meta.stale\_since} kembali \texttt{null}.
    \begin{figure}[H]
        \centering
        \includegraphics[width=0.5\textwidth]{figures/problem-2/2-6.png}
        \caption{\texttt{stale\_since} kembali \texttt{null} setelah PVMBG pulih.}
        \label{fig:stale-since-kembali-null}
    \end{figure}
\end{enumerate}
