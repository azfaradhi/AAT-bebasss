\section{Problem 3: Service-to-Service Authentication dan Trust}
\begin{infobox}{Pertanyaan Utama}
Bagaimana setiap domain kepercayaan dipisahkan sehingga kredensial antarsumber
tidak dapat dipertukarkan, sementara hak akses client downstream tetap
ditegakkan berdasarkan scope dan masa berlaku token?
\end{infobox}

\subsection{Rancangan Solusi}
Sistem memiliki tiga domain kepercayaan yang masing-masing memakai format
kredensial dan secret yang berbeda:

\begin{enumerate}
  \item \textbf{BMKG}: kunci statis pada header \texttt{X-BMKG-Key}, dicocokkan
  dengan \texttt{BMKG\_API\_KEY} di \textit{bmkg-mock}. Bearer token ditolak dengan 403.
  \item \textbf{PVMBG}: Bearer JWT HS256 dengan \texttt{aud: pvmbg}, ditandatangani
  \texttt{PVMBG\_JWT\_SECRET}. Token dibuat sekali dengan skrip
  \texttt{scripts/mint-pvmbg-token.js}. Kunci BMKG ditolak dengan 403.
  \item \textbf{Client downstream}: Bearer JWT HS256 dengan \texttt{aud: bnpb-client},
  ditandatangani \texttt{CLIENT\_JWT\_SECRET}, diterbitkan oleh \textit{auth-service}.
  Claim berisi \texttt{sub}, \texttt{scope} (\textit{media}, \textit{lapangan}, atau
  \textit{internal}), dan \texttt{purpose} (\textit{access} atau \textit{refresh}).
  TTL access token 60 detik dan refresh token 900 detik, keduanya dapat dikonfigurasi.
\end{enumerate}

Tiga client downstream adalah identitas yang benar-benar berbeda, masing-masing
dengan \texttt{client\_id} dan \texttt{client\_secret} sendiri dari environment.
Perbedaan hak akses ditegakkan di sisi BNPB, bukan oleh flag di sisi client.

\textit{Auth-service} bersifat stateless. Access dan refresh token adalah JWT yang
memverifikasi dirinya sendiri, sehingga tidak ada tabel token. Refresh memeriksa
bahwa client masih terdaftar dengan scope yang sama sebelum menerbitkan pasangan
token baru.

Di \textit{client-api}, middleware \texttt{auth.ts} memverifikasi JWT dan menyimpan
scope pada request. Middleware \texttt{rbacFilter.ts} membatasi field: scope
\textit{media} hanya menerima field Ringkasan. Permintaan eksplisit \texttt{view=raw}
dari scope \textit{media} ditolak dengan 403 \texttt{FORBIDDEN\_FIELD\_ACCESS} sebelum
panggilan ke Aggregator, sehingga data mentah tidak pernah diambil.

Setiap container hanya menerima variabel yang dibacanya. Tabel~\ref{tab:p3-secret}
merangkum pemetaan secret ke tiap service.

\subsection{Batasan yang Disadari}
\begin{enumerate}
  \item \textbf{Refresh token tidak dicabut setelah dipakai.} Refresh token lama
  tetap valid sampai \texttt{exp} (15 menit). Ini konsekuensi dari auth yang stateless
  (kontrak bagian 6.2). Jika refresh token bocor, penyerang bisa memperbarui akses hingga
  15 menit. Access token lama tetap ditolak setelah TTL 60 detik, sesuai spek.
  \item \textbf{Penolakan token bergantung pada TTL, bukan blocklist.} Access token
  yang sudah dicabut secara manual tidak bisa dicabut sebelum kedaluwarsa.
  \item \textbf{Satu secret untuk semua scope client.} Kompromi \texttt{CLIENT\_JWT\_SECRET}
  berarti token scope \textit{lapangan} atau \textit{internal} bisa dipalsukan. Pemisahan
  per scope di luar cakupan M1.
  \item \textbf{Secret tetap berupa environment variable.} Tidak ada secret manager, dan
  tidak ada rotasi otomatis. Client secret bersifat statis.
  \item \textbf{Cakupan M1 hanya baca.} Ketiga client bersifat read-only, sehingga
  kompromi client belum bisa mengubah data di BNPB.
\end{enumerate}
